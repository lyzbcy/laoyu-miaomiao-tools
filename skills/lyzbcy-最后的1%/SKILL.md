# lyzbcy-最后的1%

这是一份**极限执行模式**的元 skill。启用后，"质量"是唯一的第一性原理，token 消耗、迭代轮数都不再是约束。

> 这份 skill 会消耗大量 token —— 这是设计意图，不是 bug。只有在用户明确同意的前提下才启用。

---

## 0. 启用门槛（先读这一段）

本 skill 默认**不启用**。只有以下三种情况可以进入极限执行模式：

| # | 触发条件 | 你该做的 |
|---|---------|---------|
| 1 | 用户贴出了本 skill 的路径，并明令要求使用 | 直接进入极限模式 |
| 2 | 用户完整、明确地说出"请使用 lyzbcy-最后的1%" | 直接进入极限模式 |
| 3 | 你自己判断当前任务值得用极限模式 | **必须先**向用户说明：启用后会产生大量 token 消耗（派遣子代理、反复复查、长时间运行），征得明确同意后再进入 |

任何含糊的说法（"做得认真点""仔细一点""多检查几遍"）**都不算触发**，按常规模式做即可。

进入极限模式后，第一件事是向用户口头确认："已进入极限执行模式，以质量为唯一优先，预计消耗大量 token。"

## 1. 心跳文件——防止 AI 在长任务中注意力漂移

长任务最大的敌人不是技术难题，而是**注意力漂移**：做到第 40 分钟，AI 已经忘了开发者当初为什么要求做这件事，开始机械地"完成任务"而不是"完成初心"。

防御机制：**每当上下文占用超过 60%，必须重读项目的初心文档。**

### 怎么找初心文档

按这个优先级在项目里找，找到第一个就停：

1. `<project>/初心与使命.md`
2. `<project>/agent.md`
3. 用户在对话里贴过的需求/规格文档
4. 如果都没有，**主动问用户**："这个项目有没有写下来的初心/使命？没有的话，请用一两句话告诉我，为什么一定要把它做到完美？"——把答案记在 `初心与使命.md` 里作为后续心跳锚点。

### 重读时要做什么

不是浏览，而是带着三个问题精读：

1. 开发者做这件事的**根本动机**是什么？（不是表面需求，是动机）
2. 我现在正在做的事，是否仍然指向这个动机？有没有跑偏到"看起来在干活、其实没推进初心"的地方？
3. 如果现在交付，距离"真正完美"还差什么？

如果发现跑偏，立刻调整方向，不要因为"已经做了一半"就硬着头皮继续走错的路。

## 2. 禁止中途停下来让用户做选择题

这是极限模式和常规模式最大的区别。

常规模式下，遇到不确定就问用户——这是好习惯。
极限模式下，**停下来等于打断心流、等于浪费用户的时间**。用户启用极限模式，就是要把决策权暂时交给你。

### 该怎么做

- **优先自己探索**：读代码、读文档、读相似实现、查官方资料、跑起来看效果。绝大多数"不确定"其实读两三个文件就能解决。
- **以项目实际为准**：项目里已有的代码风格、已有的库、已有的命名规范，永远优先于你的"通用最佳实践"。先观察再动手。
- **实在拿不定主意的事，先记下来**，继续做其他能推进项目完成度的事。等到项目其他能做的**全部做完了**，再把所有积累的问题**一次性、用选择题的形式**统一问用户。

### 什么时候可以问用户

只有两种例外：

1. **会对外造成不可逆影响**的操作（发布、部署、发邮件、删数据、推到生产）——这种必须确认。
2. **所有能做的都做完了**，剩下的少数决策确实需要用户判断——这时统一问。

判断标准：**如果你停下来问的频率超过每 30 分钟一次，你已经在滥用提问权了。**

## 3. 强制的时间观念——1 小时起步

> 任务强制至少运行 1 小时。1 小时内任务不可能完美完成。

这不是为了凑时长，而是因为**真正完美的交付需要足够的探索深度**。任何在 15 分钟内宣称"完成了"的极限任务，几乎一定是浅尝辄止。

### 觉得"完成了"时，必须做的事

不要立刻宣布完成。先回头重读一遍初心文档（见 §1），然后带着这个清单自检：

- [ ] 核心功能是否真的覆盖了初心里的所有场景？还是只覆盖了 happy path？
- [ ] 边界情况、错误处理、空状态、加载状态、超时——这些"看不见但决定品质"的地方做了吗？
- [ ] 视觉/交互细节是否打磨到位？还是"能用就行"？
- [ ] 性能、可访问性、移动端适配、SEO——这些"非功能性"但决定体验的维度检查了吗？
- [ ] 代码层面：有没有重复、有没有更优雅的抽象、有没有该补的测试？
- [ ] 文档/注释：后人接手能不能看懂？

**自检后你几乎一定会发现没做好的地方。继续做。** 直到再次自检时，清单全部打钩——这才叫"完美完成"。

## 4. 疯狂的开发规范——质量第一，无视 token

### 4.1 派遣子代理是你的核心武器

极限模式下，不要单线程地"写完→自己看一遍→交差"。你应该**主动、大量地派遣子代理**：

- **代码复查子代理**：写完一个模块后，派一个子代理带着"挑刺"的心态去 review，让它专门找问题、找边界 case、找可优化的地方。子代理的反馈要当成一等公民对待。
- **测试子代理**：派一个子代理专门写测试/跑验证，覆盖你没想到的场景。
- **并行的探索子代理**：当有多个独立的探索方向（比如"调研 A 方案"和"调研 B 方案"），用 `dispatching-parallel-agents` 的方式并行派出去，不要串行浪费时间。

> 子代理消耗 token 是设计意图。极限模式下，**质量 > token**。

### 4.2 与其他 skill 协同

极限模式不是孤立运行的，它应该主动调用其他 skill 来强化自己：

- 写功能/修 bug 前 → `test-driven-development`（先写测试）
- 遇到 bug/异常行为 → `systematic-debugging`（系统化排查，不要瞎猜）
- 完成一块工作 → `requesting-code-review`（派子代理正式复查）
- 准备宣称完成 → `verification-before-completion`（跑验证、看输出，证据先于断言）
- 有多个独立任务 → `dispatching-parallel-agents`（并行派遣）

这些 skill 是工具，极限模式下要**主动想起来用**，不要等用户提醒。

## 5. 诚实可信协议

### 不知道的就去探索，不要猜测

极限模式的"质量第一"前提是**建立在事实之上**。猜测出来的"完美"是纸糊的。

- 不确定某个 API 行为 → 读官方文档、读源码、写最小复现跑一下，而不是"我觉得应该是这样"。
- 不确定某个库能不能做某件事 → 写个最小 demo 验证。
- 不确定用户想要什么 → 以项目已有代码的实际表现为准，而不是以你的推测为准。

### 探索不出来的，先记录后继续

确实探索不出来（比如依赖外部服务、需要用户提供的数据）的事：

1. 在项目里建一个 `未决问题.md`（或追加到现有的 TODO 文件），把问题写清楚：是什么、为什么卡住、尝试过什么、需要什么才能继续。
2. **立刻继续做其他能推进项目完成度的事**——不要在卡点上原地打转消耗时间。
3. 等到项目其他能做的全部做完，再把所有未决问题统一拿给用户。

---

## 6. 进入与退出协议

### 进入时

向用户说清楚三件事：
1. 已进入极限执行模式。
2. 以质量为唯一优先，预计消耗大量 token，预计运行时间 ≥ 1 小时。
3. 中途不会用选择题打断，除非是不可逆操作或所有能做的都做完了。

### 退出时

只有满足下面**全部**条件才能宣布完成：

- 初心清单（§3 自检表）全部打钩。
- 子代理复查没有发现新的 blocker。
- 验证命令实际跑过、输出已确认（不是"应该能跑"）。
- `未决问题.md` 里只剩确实需要用户决策的事，且已整理成一次性选择题。

宣布完成时，给出一份简短的**完成报告**：做了什么、自检结果、子代理复查结论、剩余的未决问题（如果有）。

---

## 一句话总结

> 进入极限模式 = 把"完成度"逼到 100%。不停、不猜、不打断、不偷懒；该派子代理就派、该回初心就回、该跑验证就跑。token 不是约束，质量才是。
