# 制作 document：导演方案与生产依据

适用：完整制作、反复改版或多人协作，需要从磁盘接着工作时。局部换字、换封面沿用现有记录，不为填表扩张任务。document 是制作文档，不要求生成 Word；用户需要 DOCX 时再按可用文档技能交付。

## 文档连接实际产物

项目保留一份可定位的制作文档，名称可沿用现有 `制作方案.md` 或 `document.md`。它先回答“这条片子怎样让人愿意看、看懂并获得感受”，再指导素材、分镜、表演、声音与制作顺序，不以问题登记表代替导演方案。[生产主线](workflow.md)给出各阶段的输入、产物和回改方式。入口链接当前版本、制作文档和审查记录；同一事实只维护一处，其余引用。已有分镜、WORKFLOW、closeout 与 run-summary 继续使用，不再复制一套状态。

制作文档回答以下问题，按本片需要组织，不要求固定章节：

- 观众为何点开：封面承诺的具体问题、首句首帧、首次可感知的回报在哪里，正文如何回答。写“准备测试的假设”，不要把方案判断称为已验证爆款。
- 本轮采用什么：当前脚本、音源、角色、画幅、工程及导出路径。记录来源和版本；原话、作者新要求与 Agent 建议分开。
- 如何安排注意力：每段的待解问题、观众此时看/听/算什么、信息变化和落定；判断是否重复、跳步或提前泄露答案。思考段保留明确问题，时长依据任务，不机械地每隔几秒震屏。
- 如何兑现动作与声音：按 shot id 链接口播、画面变化、声音事件、可读停留；视觉与音效需要同时发生时引用同一个事件时刻。尚未听校的点记待对齐，不把估计值写成已实测。
- 怎样算完成：实际看听范围、数学/事实依据、手机缩略图与裁切检查、阻塞与负责人。技术解码、用户采用和平台效果分别记录。

## 反馈到修改的最小记录

每个重要修改留一行“来源/版本 → 观察到的问题 → 决策 → 改动文件或 shot → 验证/未知”。用户反馈保留在私人项目；共享 skill 只留下脱敏、可迁移的判断。不要将建议记录成用户要求，也不要将已发给合作者记录成已被实现。

并行协作先划清文件归属。审查者写独立建议或候选资产，主制作合入时间线；用户已授权协作时及时回传具体证据，未授权消息时使用项目内交接文档。审查记录包含被审版本或文件指纹，以稳定 shot id 定位，时间码仅对应当时快照；重配音、重排后按新时间线重算。恢复先核对被审版本是否已更新，避免对旧粗剪重复报同一问题。建议已发送、主制作已合入和实际导出已核验分别记状态。

## 从本轮回流到技能

已有明确维护授权时，可修正技能中的冲突与有证据的缺口；否则按 [运行小结](run-summary.md) 保存候选。优先改已有决策段落，真实案例与本次数值留项目，不把一条片子的时长、贴脸占比、配色或音效密度固化成通用要求。

回流记录分清：已观察问题、已实现修复、已验证范围、仍待验证。比如“已发现渲染只保留入场后静帧”能支持检查渲染是否保留后续事件；它不能证明增加动作会提升完播。每个新文档从入口或模块导航可发现，分发清单包含该文件；保留本地版本与公开发行状态，不能把本机修改说成已发布。

收尾仍由 [run-summary](run-summary.md) 记录结果；本页负责制作过程与交接，不替代收尾账本。
