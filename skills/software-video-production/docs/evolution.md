# 复盘时重写规则

收尾目标是让下一次更会判断，同时保持读取成本可控。用户2026-10-19明确要求压缩、重排和改写，不采用逐次追加补丁的维护方式。

## 一次复盘的处理

1. 在项目或对应案例保存用户原话、所指版本、实际改动、结果、检查范围与未知。技术通过、用户采用、封面认可、公开发布和平台表现分别记录。
2. 找到已有模块中负责这一决策的段落。新证据支持时合并改写；冲突时收窄适用范围或替换旧结论；只是具体参数、账号或过程就留项目/案例。
3. 通读受影响章节，删除被新表述替代的重复规则、旧状态与临时补丁。不能只把臃肿从入口搬到另一个必读文件。
4. 入口只留执行顺序和必要边界；导航只负责定位；案例只作追溯，不要求每次全部加载。检查总读取成本与关键能力是否仍保留，压缩不以删字数本身为目标。
5. 检查链接和结构，更新版本与本机共享副本。未请求不发布技能、推远端或改其他技能的通用行为。

## 什么进入规则

| 证据性质 | 处理 |
| --- | --- |
| 当次硬约束 | 留项目，当前执行；下次重新核对 |
| 系列偏好 | 在对应决策中注明适用系列和可覆盖性 |
| 已观察结果 | 记录对象、版本、证据与范围，避免全局化 |
| Agent归因/改进想法 | 标记假设，定义下一次如何观察 |

案例采用“问题→选择→反馈/验证→结论与范围→未知”即可。失败、采用和评分属于对应版本；85分成片不能转成封面或留存证明。收到重复负反馈就修正原判断，不能继续堆“必须加角色/特效”的条款。

## 锁定、发布与清理

用户采用后锁定成片，未请求不继续剪。发布分别记录Agent保存/回读、提交审核、平台公开与用户确认；用户说已发布可以作为用户确认归档，不伪称独立核验，也不推出审核通过或传播表现。

清理按实际授权范围核对保留文件、哈希和绝对路径。泛称“清理一些工程”优先处理可重建缓存，保留源素材与重建资料；明确只留成片/封面时按该范围执行，不重复询问已授权删除。共享素材和其他项目不在范围内。可恢复归档要说明占用迁移到哪里，不能说永久删除或总存储下降。同步入口的失效链接与重建限制。
