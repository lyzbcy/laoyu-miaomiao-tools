# 运行小结与经验贡献

完整制作或改版交付后执行本页。小结是交付的一部分，经验贡献是交付后的可选步骤，不能为征集贡献拖延交片。一次作品跨多轮对话只汇总一次完整运行；用户后来继续改版，则更新同一运行记录及本轮新增内容。

## 制作接发布：最后阶段合并收尾

用户说“可以了，去全平台发布吧”等表示采用并继续发布时，本轮任务延伸到发布。调用可用的 `lyzbcy-video-publish-assistant`，交接同一项目内已采用成片/封面/文案的绝对路径与指纹、当前版本、制作问题与修改记录、验收范围和未决事项。复用已有manifest和素材，不复制整套工程作为新项目。只交接任务资料；本轮维护skill或讨论流程不等于授权实际发视频。

“全平台”指本次已约定的平台列表，不自动扩到所有候选平台；沿用发布skill逐平台账号、可见性及特殊授权门禁。缺少发布skill时明确无法执行发布，保留交接待办，不宣称已交付并发布。仅制作需求仍由本skill独立收尾，不强制安装发布skill。

当前项目的 `run-summary.md` 为两阶段共用记录，记录当前视频指纹、`closeout_owner`（production/publisher）、`closeout_status`（pending/partial/complete）、`summary_sent`，以及清理/贡献是否已邀约与用户答复；这只是项目内状态，不是后台调度器。派发发布后owner设为publisher，制作段先写好，发布段补写平台结果，不覆盖制作记录或另造版本数。需要跨聊天交接时携带该文件，仍由当前用户授权调用，不擅自给其他聊天发消息。

完成当次目标后由最后阶段向用户发送一条合并消息：最终交付 → 制作问题与迭代 → 逐平台状态/链接/待办 → 最终实现与验收 → 经验价值 → 必要的清理提醒和可选贡献邀约。生产与发布经验分别评估、合并呈现；若都值得贡献，可准备一份标明两个skill范围的草案，只问一次，取得对应范围同意后用一个PR提交，并分别登记实际受益skill的贡献者名单。PR范围或清理范围没有得到同意就不执行。

待审核、提交结果不明、平台失败或未授权不能合写“全平台已公开”。在有界核验后仍有待办，先给一条合并阶段回执，`closeout_status`记partial，保留恢复资料；不无限等待，也不擅自创建监控。等目标完成，或用户明确结束本轮并接受待办，再做最终收尾。最终授权版本仍需上传/恢复、用户仍在修改或待审可能需要返修时，不清理相关成片、封面和发布断点。已收到的清理/贡献答复随记录沿用，不在第二阶段重问。

## 先完成交付，再输出小结

从本次对话、版本产物和检查记录整理，不靠记忆补写。保存到当前项目的 `run-summary.md`，并在最终回复直接给出精简小结与文件链接，不只说“见附件”。私人项目保留细节；skill包不携带这些运行记录。

小结至少包含：

| 内容 | 记录口径 |
| --- | --- |
| 交付状态 | 最终成片/封面版本与路径，已交付、用户采用或待确认分别注明；用户没评价就写未评价 |
| 用户指出的问题 | 按实际先后记录用户反馈及对应版本，概括含义，必要时在项目内留原话；Agent自检问题另列，不能归给用户；没有反馈就明确写无 |
| 迭代次数 | 按实质可评审版本计数：初版1版、后续修改N版、最终总计N+1版；逐版简述改动与原因。封面另计，横竖导出、编码重跑和抽帧不充作创意改版。历史缺失时写已确认的下限或未知，不从文件名v8倒推做过8版 |
| 最终如何实现 | 说明关键取舍、素材如何组织、剪辑/镜头/字幕/音频如何实现、实际用到的组件及最终解决了什么；不堆工具名称，不把计划写成已执行 |
| 验证与未知 | 实际技术检查、视听范围、用户认可及未解决项分别写；不把解码、抽帧或交片等同完整听审、采用或传播效果 |
| 发布结果（如有） | 逐平台列本次账号、授权目标、稿件ID/实际链接和证据所支持的状态，区分草稿、已提交、审核中、公开可见及失败；缺制作历史的独立投稿不编造剪辑版数 |
| 经验价值 | 值得贡献、暂需验证或仅本项目适用，并给出具体理由；价值来自可迁移的判断或可复用修复，不来自耗时长、改版多或自评分高 |
| 存储收尾 | 当前项目旧版本数量、候选文件实际大小合计、保留项及是否已获清理授权；无法测量时注明未知，不按“每版约1G”乘版本数估造 |

未完成、受阻或用户取消时输出实际进度与未完成原因，不写“完全做完”，不触发交付后的贡献邀约。交付完成但用户尚未评价，可以输出小结并注明待评价；仅凭待确认结果不宣称方案有效，有其他独立可验证的技术经验时可单独评估。

简短表达示例（不是每次固定照抄的内容）：

> 本次已交付成片v3：初版1版、修改2版；封面另做2版。用户指出v1界面太小、v2字效抢重点；最终保留真实截图，用局部聚焦说明操作，短字效落定后再展示结果。技术解码和切点抽帧已检查，完整听审未做，用户已采用成片、封面待确认。经验可迁移到同类竖屏演示，但只对本次素材验证，尚无留存数据。

## 旧版本多或占用大时，主动提醒清理

最终交付后盘点本项目的旧成片、预览导出和可重建渲染缓存；接续发布时等统一收尾再提醒，保护仍待上传、审核恢复或返修的版本与发布断点。只检查项目范围，不全盘扫描、不跟随链接进入共享素材或其他项目。按文件实际大小登记候选绝对路径、对应版本和用途；版本数与文件数分开，不能从目录名判断整目录可删。

有至少3个已被替代的评审版本，或可清理候选合计达到约2GiB时，默认主动提醒；这是可调整的提醒参考，不是删除门槛。即便版本少，单版很大、磁盘空间紧张或用户另有要求，也应提醒。占用很小且版本少则在小结记清即可，不反复打断。文件大小合计只作预计可释放空间；硬链接、压缩、回收站或同步副本会影响实际释放，不把估计当实测。

先列出保留项：最终已交付的成片和封面、源素材、最终工程/脚本/时间轴/配置、素材与授权清单、运行小结及必要验证证据；旧版本中仍被最终工程引用的文件不列入候选。源音频、字体、角色素材和共用依赖也不能当缓存删除。可重建的旧导出、重复预览和渲染缓存优先列候选；未确认用途的目录留待核实。

提醒需让用户能作具体选择，例如（以下数字仅为格式示例，正式输出必须实测）：

> 本次交付已结束。项目还保留12个旧评审版本，旧导出和可重建缓存合计约10.8GiB。建议保留最终v13、封面v2及源素材和最终工程，清理清单中的旧导出与缓存，预计释放约10.8GiB。需要我按这份清单清理吗？也可以额外保留一个回退版。

在项目保存 `cleanup-plan.md`，含测量范围、候选路径、大小、保留项、引用检查与未知，再给出一次简短提醒。PR贡献与清理是两个独立选择，同意一个不授权另一个；可放在同一收尾消息中分别表达，不默认捆绑。

用户没答复或拒绝时不删除、不反复催问。此前已明确批准本项目清理范围的，核对清单后按原授权执行，不要求再确认。执行前解析绝对路径并验证仍在批准范围，重新检查最终文件及重建资料不被误删；清理后核对保留项可用，记录实际处理文件与释放空间。只移入回收站或同盘归档时说明尚未释放相应空间；Syncthing等同步目录的删除会传播，纳入清单说明并保护其他项目与运行目录。详细执行边界见[evolution](evolution.md)。

## 判断是否值得贡献

先查对应已有规则/案例，判断是否补上真实缺口。值得贡献的经验应有实际问题与解决证据、说明可迁移条件，并提供已有内容没有覆盖的价值，例如新的可靠镜头配方、已定位的渲染兼容修复、经反馈验证的剪辑决策，或能减少同类返工的检查方法。

只换文案/颜色、个人角色偏好、尚未试过的创意、已被现有规则覆盖的问题，通常留项目。只在一个项目成立的结论收窄范围；未验证想法可以记录为待验证候选，不包装成最佳实践。负面案例若能明确说明失败条件，也可有价值。

## 值得时，准备草案再询问

在本次专属 `.contribution-tmp/<run-id>/contribution-draft.md` 准备可审阅的小草案：问题与适用条件、做过的尝试、最终方案、验证范围/未知、准备修改的skill文件及精简候选差异、拟署名位置。按[evolution](evolution.md)优先改写现有规则，不逐条叠加通用“必须”。此时只生成项目内草案，不自动改已安装skill、不联网提交或公开附件。

草案先脱敏：去掉身份、账号、私聊原文、私密路径、密钥和客户资料；不上传原视频、人物图、截图或完整聊天记录。保留足够复现的合成例子、参数和公开来源。用户反馈可抽象为通用问题，公开引用原话或使用其素材须另有明确授权。

用户确认最终交付或本轮任务结束后，只在经验值得贡献时询问一次，并让用户知道准备公开什么：

> 本次“……问题的……修复”值得沉淀，已整理脱敏草案（链接），拟改……。你愿意将它作为PR贡献给这个skill吗？经维护者审核合入后，你会按确认的名字或GitHub账号列入skill贡献者名单；也可以匿名。未经同意不会提交。

同意才进入提交流程；拒绝、不答复或只说片子不错，均不视为同意公开。拒绝后照常结束交付，不追问、不影响使用；同一作品不反复邀约。普通“帮我做片”不是提交PR、上传素材或修改共享skill的授权。本页要求的贡献确认仅用于未来用户的贡献提交，不阻止已明确授权的skill维护工作。

## 同意后的PR与署名

目标仓库：[lyzbcy/laoyu-miaomiao-tools](https://github.com/lyzbcy/laoyu-miaomiao-tools)，目标目录 `skills/software-video-production/`。先核对用户同意公开的草案范围和署名；默认可用用户确认的GitHub账号，不从本机用户名、邮箱或素材中的姓名推断身份。未确认署名先在本地准备内容，确认后再公开；匿名也是有效选择。

将规则/案例改动与 `CONTRIBUTORS.md` 的新增署名放在同一个PR，按项目打包约定更新必要清单；一个人只留一条，关联贡献说明与PR。PR说明写明问题、方案、证据、适用范围和未知，并注明脱敏。需要代码变更时运行相应检查；纯经验文档不要求重渲染整片。不重传未授权资料、不自动合并、不绕过维护者审核。

优先用用户自己的账号fork与分支提交；在有写权限的现有工作副本操作也应创建贡献分支，保留他人改动。身份、权限或网络不足就交付补丁及可复制PR正文，明确“尚未提交”，不能假称PR已创建。实际创建PR后返回链接；工具可用时按环境要求附加PR到当前聊天。

“邀请贡献”“用户同意”“PR已提交”“已合入并正式署名”分别报告。PR中的名单只是拟新增，合入后才进入正式贡献者名单；维护者合并时核对本人署名意愿和名单条目，遗漏时在发布前补齐。用户只愿意分享经验、不愿署名时按匿名登记贡献，不公开身份。


## 跨skill去重与最终确认

多个skill串联时共用同一项目、运行ID与 `run-summary.md`，只由 `closeout_owner` 所指的最后阶段发送完整收尾；前序skill只补记录。共享记录增加 `final_delivery_confirmed`、`contribution_invitation_status`（not_offered/offered/accepted/declined）、`contribution_scope`、`contribution_temp_paths`、`contribution_cleanup_status`（not_created/pending/cleaned/failed）与提交结果。已收到的答复、已清理状态沿用，不因换skill重建贡献包、重复邀约或重复提醒。

`summary_sent` 仅表示完整最终小结已发送；partial阶段回执不能置为true，以免吞掉后续最终收尾。投稿仍有待办时给合并阶段回执；目标完成或用户接受待办结束本轮后，最后阶段才发送一次完整小结。发送后及时登记状态。恢复时先读记录；发送是否成功不明时先核实，不直接重发。

PR邀请必须等用户确认最终交付/本轮任务结束，不能把文件生成、上传完成或制作通过视为整个发布任务已获确认。“可以了，去全平台发布吧”只确认制作并延伸任务，等发布收尾获确认再邀请。若最终小结已发送但用户尚未确认，先不邀请；确认后可单独补一次简短邀请，不重发整份小结。用户随后对贡献或清理的答复需要处理并回报结果，这类简短执行回执不算第二次完整收尾。

## 用户答复后的临时贡献包清理

本节落实“集思广益提pr”组件。制作与发布共用本次专属 `.contribution-tmp/<run-id>/` 和创建清单，草案为其中的 `contribution-draft.md`；不各建一包。只准备脱敏短文本及必要候选差异，不复制视频、源素材或整个工程。运行记录保存目录绝对路径和自己创建的文件清单；正式交付不能放进临时目录。

- 用户拒绝：记录不提交，清理本次临时贡献草案、包和打包缓存，停止邀请。
- 用户同意：先完成获准范围的PR或补丁交付，记录PR链接/补丁交付及署名意愿，再清理临时包与一次性副本；不得先删除唯一待提交补丁。只同意其中一个skill，就只提交该范围，其余临时候选也在处理完答复后清理。正式贡献者以审核合入为准。
- 提交失败：如实记录未提交和失败原因，将最小可用文字补丁保存在项目运行记录或正式补丁交付中，再清理大包和打包缓存；用户明确要求保留的按其要求处理。
- 用户未答复：不提交、不把沉默当同意或拒绝，不反复催问；无需一直等待，避免生成或持有大包，后续收到答复按上述分支处理。只答复旧版本清理不代表答复了贡献邀请，两个选择分别登记。

这类由本次贡献流程创建的临时文件，答复后清理属于组件收尾，不再要求第二次清理授权。执行前解析并核对绝对路径属于本次专属目录，按创建清单处理，不跟随链接或删除目录外内容；同步目录删除会传播。保留最终交付、源素材、既有仓库与依赖、账号凭据、运行小结、PR链接及必要提交结果。清理失败记failed与残留路径，不能声称已清理。记录完成后只简短回报“已提交/未提交，临时贡献包已清理”；没有创建包就写无需清理。

**旧视频版本清理是另一件事**：仍按 `cleanup-plan.md` 的具体范围取得用户同意；同意贡献不授权删旧片，同意删旧片不授权提交PR。上面自动清理的范围仅限本次自建临时贡献文件。

## 持久化收尾检查

同一项目的制作和发布共用一份closeout.json。制作workflow初始化时即创建，发布接续只恢复，不重置。每次恢复先status，准备结束前audit：

```powershell
python scripts/closeout.py init LEDGER
python scripts/closeout.py status LEDGER
python scripts/closeout.py record LEDGER --task experience_review --status valuable --evidence ASSESSMENT.md
python scripts/closeout.py record LEDGER --task contribution --status approved --evidence USER_CONSENT.json
python scripts/closeout.py record LEDGER --task contribution --status submitted --evidence PR_RECEIPT.json --url https://github.com/OWNER/REPO/pull/NUMBER
python scripts/closeout.py audit LEDGER
```

init只在新运行首次执行；已有账本再次init会拒绝，不覆盖决策。status返回紧凑未决项；audit有未决或证据变化时非零退出。任务包含交付确认、经验评估、贡献、归档、旧片清理和临时贡献包清理。经验无复用价值可明确not_valuable后not_needed；用户拒绝记declined；已有明确授权沿用，不重复邀约。投稿或合集审核待办与可执行收尾项分别记录，不能因一个partial吞掉其余收尾检查，也不为越过最终确认时机提前邀约。

归档verified使用JSON索引的files数组，每项path和sha256须对应真实保留文件；就地索引、打包和物理迁移分别报告，不把索引称为已搬走工作区。清理cleaned的JSON回执含deleted路径数组，脚本核对这些路径确已不存在；awaiting_consent不能算已清理。retained只用于用户明确决定保留，不能把未回答改成保留授权。PR submitted必须保留单独的用户授权证据及实际PR链接。归档或清理的实质操作仍由当前授权范围决定，脚本不自动发PR、删文件、催用户或创建后台调度。

新任务在项目入口记录固定恢复与收尾命令，使下一次从磁盘定位，而非仅依赖聊天摘要。账本不是后台自动执行器；若Agent不调用入口，仍可能漏，因此SKILL入口与交付步骤都显式路由到status/audit。贡献授权、PR提交、合入和正式发行仍分开，不能因门禁通过就宣称已合入。
